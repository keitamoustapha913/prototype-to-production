# Prototype to Production

Turn a runnable frontend prototype into a precise, recoverable implementation contract. Be creative **before approval**, faithful **after approval**. Unspecified approved layout or interaction details are blockers, not creative freedom for the implementer.

## Short requests are complete requests

A user can simply say **“Redesign the billing page using these reference images”**, **“Prototype this app with a bold editorial look”**, **“Review prototype v1”**, or **“Implement the approved prototype.”** Do not make them write an initiative ID, stage list, source filename, validation checklist, or an 80-line prompt. Infer the real app, page/feature scope and stable initiative ID by inspecting the open repository and conversation/artifacts. Ask one focused question only when the target or design direction cannot safely be identified.

**Design direction comes from the current user and this initiative's references**, never from the skill, a previous app, or an earlier test case. Any visual style is eligible: dense or spacious, minimalist or expressive, formal or playful. If a style is not specified and cannot be inferred from supplied references or a request to retain the existing style, ask a focused question. Record the agreed direction in initiative-local decisions and prototype evidence; do not carry another project's aesthetic forward.

Default route for a new redesign: **source/browser-discover A → freeze complete A functionality → build runnable B from A → verify every A behavior in B → verify visually → present a short review → STOP for explicit approval**. **Prototype approval presentation is blocked until every in-scope A behavior has a verified B counterpart.** The user must never have to provide a lengthy features checklist or repeatedly point out features already present in A. “Review” means inspect evidence and request revisions or user approval, never approve on the user's behalf. “Implement” means resume/validate the exact prior approval, specify slices, implement and verify without restyling. Auto-resume existing initiatives before acting; never restart based solely on chat memory. See `references/workflow.md` and `references/functionality-discovery.md`.

## Start here every time

1. Read `references/workflow.md`, `references/functionality-discovery.md` and `references/continuity.md`, and, before prototype capture or acceptance, `references/visual-qa.md`. Read `references/slice-contract.md` when preparing/receiving slices.
2. Inspect the real repository, source UI A, Git state and existing instructions. Locate the requested scope and style from the user's short words/images; clarify only consequential ambiguity.
3. For existing work, run `python <skill-root>/scripts/project_state.py resume --project-root <repo> --format json` (add `--initiative-id <id>` only when multiple initiatives exist), then `validate`; inspect actual code, manifest, journal, checkpoint, prototype source, screenshot hashes, **recorded blockers and side-by-side warning galleries**. Resolve discrepancies **before** work. Resume the saved phase and task; do not start over.
4. For new work, run `init --scope <feature|page|app>` and use the **directory it prints**. In any Git repository (including the main checkout), the script places new artifacts under ignored `.artifacts/prototype-to-production/<id>/`. All generated design documents, plans, runnable prototype source/CSS/assets, screenshots, browser results, fixtures, inputs and handoffs belong inside the initiative directory. Paths such as `prototype/versions/` are relative to that directory, never the repo root. This artifact-location rule also applies when another planning or design workflow suggests tracked `docs/`, `design/`, or app source paths. Only the approved implementation belongs in tracked app code. Before creating any artifact, confirm its destination is untracked and ignored with `git ls-files -- <path>` and `git check-ignore -- <path>`. Existing legacy initiatives may stay in place only when untracked and ignored; stop for reconciliation if tracked. Do not write project evidence into the installed skill or silently change tracked `AGENTS.md`/`.gitignore`.

## Stage router

| Stage | Actions and hard gate |
| --- | --- |
| Discover | **Mandatory:** trace all in-scope A routes, controls, permissions, validation, backend effects and states through source **and** a real browser. Freeze source anchors, observation evidence and a complete zero-new-feature final sweep with `discovery-record --audit-file <json>`. If incomplete or unresolved: **BLOCKED**, not ready to design B. |
| Prototype | Build runnable B **from A functionality**, not an independent fake redesign. **Mandatory:** map **every** frozen A feature to real B source and a passing exercised interaction, then run `prototype-coverage --coverage-file <json>` for the exact version. Until it succeeds, do **not** present B as approval-ready. Inspect mobile, tablet, desktop, long copy and roles. Save replayable fixtures, browser screenshots and source; **exclude QA-only controls from product reference captures**. |
| Approve | Require explicit user approval of the exact B version/cases **after mandatory A-to-B parity**. `approve --approval-file <json>` refuses missing/stale A audits or B coverage, and for source mode requires two clean-context replay runs and QA-free screenshots, all SHA-locked. Image-only requires a separately approved exception. |
| Specify | Extract exact tokens and patterns; map A behaviors to B. Run `slice-create --contract-file <json>` for self-contained vertical slices with screenshots, source paths, file ownership, dependencies, acceptance checks. Unspecified visual patterns remain blocked. |
| Implement | Prefer prototype code reuse, preserve all app functionality, respect isolated file ownership and user modifications. Workers use `slice-report` for slice-local evidence; coordinator uses `reconcile --action report`. |
| Verify | Match **exact approved B cases** to the same implemented route/fixture/state; check unchanged A pages only against their own A baselines. Diagnose mismatches and retry three times in clean contexts. Record real defects through `reconcile --action block` so the official task status and checkpoint agree. Approved B-case capture warnings receive an automatic SHA-locked **side-by-side HTML comparison gallery**; record other material warnings, including ancillary A-before/A-after warnings, with `warning-record`. Real UI defects/missing evidence are **BLOCKED**. Narrow B-case capture warnings may be provisional, never PASS. See `references/visual-qa.md`. |
| Integrate | Check accepted slices, live Git/code state, shared patterns, and user review. Pending warning galleries require explicit `warning-decide` before slice acceptance; a provisional B-case warning also needs `accept-warning`. Confirm evidence hashes with `validate`. No implicit commits, merges, deployment, or agent spawning. |

After **every material** choice, revision, blocker, or completed task, record `event` and `checkpoint` using `scripts/project_state.py`. Project files, hashes and code outrank chat context. Ignored files persist across sessions **in the same workspace**, not automatically across clones, machines or isolated worktrees: arrange a verified external handoff of the whole initiative when workers cannot share the directory; otherwise report **BLOCKED**.

**Mandatory crash/compaction survival:** Before beginning a substantive task, and after **each meaningful step or long tool operation**, run `work-update --work-file <json>` using `assets/project/work.template.json` with the actual phase, task ID, status, completed and pending steps, next action, code/evidence paths, and blockers. Refresh it **before potential context compaction or planned interruption**; never leave the only continuation point in conversation. `work-update` serializes updates, appends to the journal, and safely replaces the manifest/checkpoint files. In a new session, run `resume --project-root <repo> --format json`; inspect `active_work`, `safe_to_continue`, earlier decisions (and full decision journal), approved artifacts and reconciliation warnings, then **continue its exact unfinished task without redoing completed steps**. If it reports `waiting_user`, blocked evidence, conflicting files or multiple initiatives, stop and resolve only that issue. Never invent approval or overwrite earlier decisions. See `references/continuity.md`.

**If functionality is missed after approval:** immediately run `missing-feature --report-file <json>` with original A/B observation evidence. The canonical state blocks more implementation while Codex re-audits **all affected A routes/source/API paths**, including neighboring behaviors, until **one full zero-new sweep** occurs. Freeze the expanded inventory with a new `discovery-record`; restore the missing behavior in a **new B version**, re-run full `prototype-coverage`, and ask for explicit new user approval. Old approved sources, screenshots, style choices, decisions and evidence **must not** be rewritten. If no gap exists, only the user's explicit correction plus evidence may dismiss the report. See `references/functionality-discovery.md`.

## Quality bar

Evaluate the UI against **the user's chosen aesthetic**, applicable accessibility/usability requirements, and the real application's behavior. Check alignment, readability, control reachability, truthful content, focus states, responsiveness, and absence of accidental overlap/clipping. Do not impose a default palette, density, card size, typography, copy tone, or amount of whitespace. Before approval, exercise every A-derived B behavior and test 320/390/768/1024/1440px (or documented equivalent) and supported long-text locales; inspect real pixels. The **approved prototype**, not generic advice, controls final dimensions and visual character. Unreplayable fixtures, screenshots containing prototype QA controls, missing source or browser, incomplete functional coverage, stale hashes or self-review never count as acceptance.

## Included resources

- `scripts/project_state.py --help`: durable CLI state, mandatory `work-update` cursor and auto-discovering `resume`, `discovery-record` / `prototype-coverage`, postapproval `missing-feature` recovery, approval, slices, verification and validation.
- `assets/project/work.template.json`, `discovery.template.json`, `prototype-coverage.template.json`, `missing-feature.template.json`, `manifest.template.json`, `approval.template.json`, `replay.template.json`, `slice.template.json`: project-local JSON contract examples; placeholder evidence is invalid until actually observed and replaced.
- `assets/project/redesign.visual.spec.ts`: intentionally incomplete Playwright scaffold, to adapt to the app's existing browser tooling; requires actual fixture/state setup.
- `references/functionality-discovery.md`, `workflow.md`, `continuity.md`, `slice-contract.md`, `visual-qa.md`: detailed discovery, functional parity, continuity, visual QA and implementation gates.
