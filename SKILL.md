# Prototype to Production

Turn an idea into an illustrated, approved implementation contract, then review the complete slice package before delivering small verified slices. New initiatives use **blueprint-first**; a complete runnable clone is optional. Existing initiatives without a mode retain their original **prototype** semantics and approval locks.

## Start and route

1. Inspect repository instructions, Git state, relevant source, tests and existing initiative evidence. First try `python3 <skill-root>/scripts/project_state.py resume --project-root <repo> --format json`; select an ID only if ambiguous. Resume the exact saved task and pending question. Run `validate` before continuing; reconcile changed/missing evidence instead of restarting.
2. Read [references/blueprint-workflow.md](references/blueprint-workflow.md) for the default route and [references/guided-design-review.md](references/guided-design-review.md) before discussing discovery, roadmap, blueprint or slices. Read [references/continuity.md](references/continuity.md) for checkpoints, interruptions and transfer.
3. Initialize a new blueprint initiative with `init --project-root <repo> --initiative-id <id> --scope <feature|page|app> --guided-design-review` to require recorded terminal review evidence. For the explicit full runnable-B route, use `--mode prototype` in place of `--guided-design-review`, then read [references/workflow.md](references/workflow.md), [references/functionality-discovery.md](references/functionality-discovery.md), and [references/visual-qa.md](references/visual-qa.md). Preserve the mode and approvals of existing initiatives. Apply the guided conversation to their unfinished design reviews.
4. Use the **directory printed by init/resume**. In any Git repository, generated design documents, plans, diagrams, prototype source, preview assets, screenshots, fixtures, JSON inputs and handoffs belong under ignored `.artifacts/prototype-to-production/<id>/` or the existing ignored initiative path. Template paths are relative to that directory. This rule applies when another workflow suggests tracked `docs/` or `design/`. Confirm each destination with `git ls-files -- <path>` (empty) and `git check-ignore -- <path>` (matched). Only approved implementation goes in tracked app code. The CLI guards every command and refuses tracked artifacts; never untrack or move legacy evidence automatically.

For every new initiative or resumed intake, run [Initial Understanding and Alignment](references/initial-alignment.md). Investigate the brief and repository, map every requirement to evidence, and discuss the findings in Codex CLI. Wait for explicit confirmation of the current understanding before freezing discovery, planning or generating a blueprint. A correction requires a revised map, a fresh presentation and fresh confirmation.

For an explicit small request, keep the roadmap and feature contract short. Use a single workstream when it covers the request. Apply the same conversation checkpoints, then run the baseline, plan, blueprint, coverage and validation commands at their respective stages. If a command remains blocked, show the draft and the exact blocker.

## Blueprint-first route

**Investigate → confirm initial understanding → review discovery → complete conversational implementation-plan review → explicit Continue to blueprint → present coverage overview → walk through blueprint workstreams → audit consistency and coverage → explicit blueprint approval → all slice proposals → one-by-one review → collection validation → package approval and lock → separate start authorization → release, implement and verify.**

- **Investigate before asking.** Discover in-scope behavior from actual source and browser/API/test evidence. Explain findings in simple terms. For existing A, inventory stable feature IDs, hidden controls, roles, states and backend effects, with a final full zero-new sweep. For greenfield, verify an empty A baseline and derive requirement IDs from recorded user intent. Use `discovery-capture` for named browser states and roles. Backend-only work uses source and API evidence.
- **Preserve the original UI.** Use [Visual Baseline Capture](references/visual-baseline.md) during discovery of existing UI. Capture relevant screens, component details and interaction states, then link the selected immutable captures or explicit gaps to the discovery audit. Resume with the saved originals, approved design and implementation captures.
- **Lead with the terminal conversation.** Explain your understanding, findings, proposal and preservation boundaries in plain language. Use a compact plain-text sketch, table or example. Link exact document paths and the viewer for depth. Invite one consequential correction or decision at a time. Give the user a turn to correct discovery before freezing the baseline with `discovery-record`. Scale detail to complexity.
- **Record exact consequential exchanges immediately.** `conversation-record` preserves the displayed question/proposal, options, recommendation, tradeoffs, illustrations and actual response. Answers and corrections are new linked records; earlier questions, rejected options and decisions remain unchanged. Give short decision recaps after discovery, before approval and after amendments. Preserve the full transcript only on explicit request through a supported mechanism; disclose unavailable/partial capture. Never fabricate missing exchanges. During blueprint and slice review, capture deliberate visual or interaction differences as protected decisions on the A+ exchange. Confirm ambiguous intent, then carry the exact protected property, purpose and verification into each affected blueprint feature and slice guide.
- **Keep visual corrections lightweight.** Start the persistent [living review viewer](references/living-review.md) for blueprint and slice discussion. Edit affected sources, show the automatic focused comparison and review evidenced cross-slice impact. Save consequential decisions and the exact displayed revision. Run scoped checks at approval and complete-package checks before lock.
- **Review the implementation plan before drafting the blueprint.** Follow [Complete Conversational Implementation-Plan Review](references/implementation-plan-review.md). Show the full proposed roadmap, then discuss one workstream at a time. Wait for explicit **Continue** on each workstream. Verify complete requirement and acceptance-scenario coverage, consistent dependencies and recorded decisions. Wait for the separate **Continue to blueprint** instruction before drafting or recording the blueprint. Request explicit permission before a temporary isolated runnable experiment; treat its output as disposable evidence.
- **Trace every source item through the blueprint.** Follow [requirement traceability](references/blueprint-workflow.md#complete-requirement-to-blueprint-traceability) from intake through final acceptance. Give requirements, constraints, decisions and individual acceptance scenarios stable IDs. Record the coverage audit and show the workstream overview, verified counts and gaps before the first walkthrough. The Markdown and viewer retain the exact section and check for each item.
- **Walk through one blueprint workstream at a time.** Explain and illustrate the current workstream, apply corrections, recap and save the actual presentation and pending question. Wait for explicit **Continue** or equivalent before advancing, including after the final workstream. Honor explicit scoped skips and revisits. Audit the final blueprint against the full sources and all reviewed workstreams. Ask for separate approval of the exact version with its coverage report and decision recap only after the audit clears every material gap.
- **Review the complete slice inventory.** After blueprint approval, follow [the slice review workflow](references/slice-review-workflow.md) and [the guide and delivery contract](references/slice-contract.md). Draft every illustrated guide and proposal before the first slice review. Discuss one slice at a time unless the user explicitly delegates a named scope. Approval advances the review. Review, lock, and start are separate user decisions.
- **Release exact assignments.** The reviewed collection must pass validation and receive package approval before locking. Present the exact package hash and wait for the separate instruction to start. Run `slice-release` for each slice when its locked dependencies are accepted. Before dispatch or source changes, read the locked guide and contract and run `resume` and `validate`. Material discoveries follow a versioned amendment. Legacy blueprint initiatives retain their delivery path unless the user explicitly migrates.
- **Verify actual results.** Blueprint reconciliation runs approved check commands and captures UI render evidence where applicable. Use `reconcile --action block` or `unblock` for defects. Final acceptance requires independent review, successful execution and unchanged source and evidence hashes.

Before any edit to shared UI source, run [Cross-Screen Visual Regression Protection](references/cross-screen-regression.md). Trace affected screens and slices, register the change, reuse intact originals and capture any missing states. Run the pre-edit readiness check. Apply this to routine implementation, redesign, refactoring and repairs. Recheck every affected case, repair confirmed defects within approved boundaries, and preserve the evidence in the viewer. Missing essential originals or failed checks hold affected work while eligible independent slices continue.

For **every UI-changing implementation slice**, apply the [Visual Integrity Gate](references/visual-integrity.md) before verification. Choose coverage by changed component, critical state, actual interaction and supported viewport. Include every approved case and check. Compare real browser observations with the locked blueprint and protected decisions before repairing confirmed defects. Save annotated comparisons and outstanding concerns in the Visual Review Register. Continue independent assignments while an unresolved or incompletely verified repair holds its slice and dependent work.

## Preserved full-prototype route

At slice verification and before reporting application completion, follow [Final Visual Quality Standards](references/visual-quality.md). Run the final audit against current evidence. Documented nonblocking warnings permit technical completion. Open [Application Completion Review](references/final-review.md) automatically after a passing audit. Guide the user through only the scope they request. Record corrections before editing and preserve the revalidation and comparison. Record final acceptance only from the user's explicit decision on the exact current report.

For `prototype` initiatives: discover and freeze A → build runnable B → exercise every A feature → `prototype-coverage` → two clean-context replays with QA controls excluded → explicit exact-version source/image-only approval → slices → approved-B visual/functional verification. The original screenshot, replay, warning-gallery and user-warning-acceptance gates still apply. Blueprint coverage cannot substitute for runnable A-to-B parity in this mode.

Design direction comes from the current user and this initiative's references. Before approval, propose values clearly; after approval, preserve exact choices. No aesthetic from another app is a default.

## Continuity and gaps

Run `work-update` before substantial work and after each meaningful step, test, blocker or decision, including before context compaction when possible. Save phase, task ID, completed/pending steps, code/evidence paths, next action and blockers; for a user question, save `pending_question_id` and `waiting_user`. On resume, restore the exact question/answer and unfinished task, not a fresh questionnaire.

If functionality was missed after approval, run `missing-feature`, re-audit the affected scope until one full zero-new sweep, and preserve prior decisions. Real gaps require a new blueprint or prototype version with full mode-specific coverage and fresh explicit user approval. False reports need an explicit evidenced user correction. Do not silently dismiss reports or revise locked artifacts.

Ignored evidence survives sessions in the same workspace, not Git clones or independent worktrees. Transfer/export the entire initiative through an authorized channel and validate hashes before cross-workspace work. Hashes detect change; they are not backups. No implicit commit, merge, deployment, installation or agent spawning.
