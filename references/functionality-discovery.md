# Functionality-first A-to-B discovery and parity gate

This procedure is **mandatory for every new prototype approval**, whether the request covers one control, one page or an entire app. The user gives the design direction, not a list of existing features. Codex must discover application A's behaviors from real code and browser operation before designing B. A prototype is **not approval-ready** until `discovery-record` and `prototype-coverage` both succeed for the exact version to be shown.

## Source-led inventory of application A

1. Identify the exact requested boundary and all in-scope routes, navigation paths, nested views, dialogs and actions, including controls that appear only after hover, selection, an error or a role change. For an app-wide redesign, enumerate every reachable section. Investigate inaccessible routes and capture blockers honestly.
2. Trace each UI control from rendered label/icon through event handler, state changes, validation and mutations to its API endpoint, backend permission/transition rules, database updates, errors and navigation. Inspect frontend components/hooks, backend routers/services/models, tests and flags. Cross-check source-visible functionality against browser-visible behavior; an omitted modal or backend action is still functionality.
3. Run A in a browser with safe fixtures. Exercise each in-scope role, realistic data shape, empty/loading/error/success state, locale and responsive state that changes interaction. Capture real observations (screenshots and, where useful, trace/results) under `discovery/evidence/`. Never modify production data just to create test evidence. Every feature record needs a stable ID, real route, behavior, roles, states, matching source anchors and browser evidence. List unresolved functionality explicitly—**unresolved means BLOCKED**, not “probably not needed.”
4. Record the first discovery sweep across **all** in-scope routes and relevant source files, then revisit the entire boundary in a second independent sweep. New features found during a sweep are added to the inventory, not ignored. Continue until **one full zero-new sweep** finds no additional behavior. For a postapproval follow-up, at least one complete zero-new sweep is required; repeat while additions still turn up.
5. Save `discovery/audits/<audit-id>.json` via `python <skill-root>/scripts/project_state.py discovery-record --project-root <repo> --initiative-id <id> --audit-file <real-json>`. The CLI checks all feature IDs, code anchors, browser evidence paths, scope and sweeps; it hashes immutable A audit and observation files. Use `assets/project/discovery.template.json` as an **invalid placeholder example**, not as discovery results. Never claim complete inspection based on a file listing or static screenshot alone.

## Build B from actual A, then prove behavioral parity

1. Use A's routes, data types, working actions, domain logic and role rules as the behavioral starting point. You may redesign the arrangement and visual style from the user's direction, but do not invent a fresh fake app with dead buttons. A separate runnable preview can use isolated test data; its controls must still reproduce the observed state transitions and outcomes.
2. Make a **one-to-one A-feature to B-behavior mapping** from the frozen audit. For every feature ID, identify the runnable B source path, which role and state were tested, actions exercised, actual result and test command/report. Explicitly handle failures and dependencies, not just the visible default page. Keep the coverage file in `coverage/versions/<version>.json` and passing browser/interaction reports in `coverage/evidence/<version>/`.
3. Run `prototype-coverage --coverage-file <real-json>` for that **exact prototype version**, using `assets/project/prototype-coverage.template.json`. The CLI rejects missing/duplicate feature mappings, missing B source, non-PASS proof, stale A audits and fake unsupported exceptions. Where the user knowingly chooses an image-only proof instead of runnable B, record a separate **explicit image-only user decision** and its exact exceptions; never silently treat an image as working functionality.
4. Only after the parity gate, actual viewport/role visual replays, and source preservation may Codex **present B as ready for approval**. Do not ask the user to rediscover application A's forgotten controls as a substitute for this work. If any functionality is still unknown, record a blocker, investigate it, and show a *work in progress* only (not a pass or an approval request).
5. The approval CLI checks the latest A audit and exact B parity contract before locking the user's **real** approval. Visual replay alone cannot bypass this functional gate. Freeze source, evidence, hashes and user note. The tool validates internally consistent evidence; **the agent must genuinely perform observation and tests**—a fabricated `PASS` JSON would be dishonest and is not proof.

## Missing functionality discovered after approval

1. Never change or revoke a previously approved layout, behavior or user decision on your own. First preserve the reported mismatch with `missing-feature --report-file <json>` (`assets/project/missing-feature.template.json`). It stores an immutable report and hashed observation evidence and sets the canonical manifest/checkpoint to `coverage_pending`, blocking new implementation or final acceptance. Already accepted historical decisions remain intact.
2. Reopen A's inventory and inspect the **whole affected boundary**, including adjacent routes, dialogs, permissions, data handlers, backend effects and tests. A missed feature is a signal that others may be missing. Add the observed features as **new stable IDs** to a fresh complete audit. Never delete or overwrite previous A feature records. Repeat full sweeps while finding new IDs; finish with **one full zero-new sweep**. Save with a new `discovery-record` audit ID.
   If production files have already changed, rely on the **frozen, hashed earlier A audit** for previously verified A behaviors and inspect original A source snapshots/backups where available; do not relabel the new B implementation as A. Newly found A behaviors still require genuine source/browser evidence. An unchanged old feature record need not re-match mutated production source text, but its original evidence remains protected.
3. If the report is a real gap, restore that A functionality in a **new B prototype version** and replay **every** feature from the updated A inventory, not just the one reported. Freeze new `prototype-coverage`, visually verify again and ask the user to approve the new B version explicitly. The former approval stays preserved and unmodified. The new approval may clear `coverage_pending` only after the fresh audit and mapping account for each reported feature.
4. If the investigation finds no gap, the report does **not** disappear automatically. **Never silently dismiss** a user's report or interpret a clean sweep as permission to override it. Ask the user to explicitly correct/withdraw the report; then the new audit can contain `missing_report_resolutions` with `report_id`, `resolution: "not_missing"`, `confirmed_by_user: true`, the real `user_note` and hashed `evidence_paths`. After a full zero-new sweep and this explicit user correction, the existing approved version may safely resume.
5. If a reported feature is already in A's old inventory but B's interaction was missing or incorrectly tested, it **still requires a corrected new B version, fresh passing proof and explicit reapproval**; matching A feature IDs alone does not excuse the gap. No approval of another version is allowed before the required follow-up discovery.

## User decisions have precedence

- Keep the original user-approved B version, screenshots, tests and style rules immutable. No agent may silently revise, supersede, or retroactively describe a decision differently. A later design correction creates a separate version and explicit user decision.
- Preserve previous A feature definitions unchanged in all later discovery audits; if the user intentionally changes the *product behavior* rather than only B's presentation, record the explicit correction as an addendum/new decision and ask before changing the original definition. The source inventory must describe what A actually does, not what the agent wishes it did.
- An unknown behavior, conflicting user decisions, missing evidence, stale hashes, or an incomplete postapproval sweep is a **BLOCKED** gate with a concrete next action. Do not bury ambiguity in a loose handoff plan.
- This discovery gate is mechanical **and** procedural. Hashes ensure retained evidence is unchanged, but they cannot prove that every hidden route was inspected; a real thorough source/browser sweep and independent scrutiny remain essential.
