# Blueprint-first contracts

Follow the [terminal-first guided review](guided-design-review.md) for discovery and the one-workstream-at-a-time blueprint walkthrough. Complete [Conversational Implementation-Plan Review](implementation-plan-review.md) before drafting the blueprint. Use the [living review viewer](living-review.md) for deeper inspection and focused before-and-after comparisons.

Use this route for new substantial implementation, redesign or greenfield requests, and proportionally for every explicit skill invocation. A small uninvolved fix can use the ordinary workflow. Initialize new blueprint initiatives with `init --guided-design-review`. An absent mode in an old manifest means prototype. Preserve prior approvals and apply the guided conversation to unfinished design reviews.

## Evidence-led conversation

Complete [Initial Understanding and Alignment](initial-alignment.md) before freezing discovery or planning. Carry the confirmed requirement IDs into the baseline requirements and the roadmap’s `requirement_workstreams`, keyed by requirement ID with a list of applicable workstream names. The existing blueprint coverage and slice contracts carry the IDs forward.

Inspect actual instructions, code, behavior, APIs, tests and supported browser states before asking the user for choices. Explain what exists in beginner-friendly language, then ask one context-specific question that changes the outcome. Define a technical term when first used. Separate observed facts, agent proposals, actual decisions and unresolved questions. Offer two or three source-grounded options and a recommendation when they help, with ordinary-language tradeoffs. Do not make the user inventory functionality the repository can reveal.

Use narrow plain-text flows, tables and outlines in the terminal. Use Markdown/Mermaid in the detailed specifications for nontrivial navigation, architecture, state and data flows. For a combined messaging example, explain the existing conversation and group hierarchy, creation action, role rules and mobile/error states before discussing a new arrangement. For an API restructuring, explain callers, authorization, request/response compatibility and failures before asking about a new service boundary. A full HTML or full-stack clone is optional.

Record each material exchange immediately through `conversation-record --exchange-file <json>`:

- Stable `exchange_id`, real `phase`, exact `question`/proposal as shown, exact `options` with `label`/`tradeoff`, and `recommendation` where offered.
- Exact actual `response` for decided/rejected records; null while open/proposed. Capture rejected alternatives and why a correction changed direction. Evidence `source_paths`, `evidence_paths` and `illustration_paths` link to real files; feature/requirement IDs identify scope. For a pending question without known affected IDs, write a concrete `scope_reason`. Link existing evidence for repository-grounded questions. When the question comes from the brief or user intent, record that basis in `basis`.
- Use `responds_to` to answer an open question. Copy the exact question or proposal into the answer's `question` field. Use `supersedes` to amend the current decision about that same question. Keep the original question, `responds_to` link and affected IDs when recording its correction. Include linked `plan_ids`, `blueprint_ids` and `slice_ids` when known. Material MODIFY/REMOVE authorization uses `authorized_changes: [{"baseline_id": "feature-id", "classification": "MODIFY"}]` on the user's actual decision.
- Status is `open`, `proposed`, `decided`, `rejected` or `superseded`. Use a new record for every answer/amendment; do not edit old records. The CLI adds timestamps and SHA-locked illustration/evidence references and checks the registry against the append-only journal. Answers retain the exact question scope; record newly introduced scope as a separate exchange. A second answer requires an explicit correction link to the earlier answer. All applicable material decisions, including later additions, must be incorporated before approval or implementation.

If the source linked to a question changes before its task resumes, inspect the change before using the answer. If the question and actual answer still apply, record the linked answer or correction with the current `source_paths`, fresh `evidence_paths`, and a `source_reconciliation` explanation. If the change introduces a material decision, bring it to the user as a separate question.

Give a short decision recap after discovery choices, before blueprint approval, and when amendments accumulate. Save recap diagrams and documents as exchange evidence. For a confirmation that leaves the design unchanged, use a decided exchange with `record_type: recap` and the actual response. Record corrections separately as linked design decisions. Plan and blueprint writers must read the full consequential exchange history, not only a summary.

Complete raw transcript preservation requires an explicit request for a specified discussion or session. If the host provides an authorized export, preserve the verified export in the initiative and link it from the related exchange's evidence. Record the session and message range, gaps, and any redactions. A user-provided export can serve the same purpose if its scope can be verified. If capture is partial or unavailable, tell the user which range can be preserved. Keep the structured exchange journal authoritative.

## Baseline and roadmap

`discovery-record --audit-file` uses a blueprint audit with `baseline_kind` and `surface` (`ui`, `backend`, `fullstack`):

- **Existing A:** use the blueprint discovery template. Trace controls, handlers, APIs, permissions, mutations, and source anchors. UI and full-stack features use browser observations. Backend features use `evidence_paths` containing API or test observations. Internal services and jobs can omit `route` and use empty `routes` and `routes_checked` when the scope has no HTTP routes. In a full-stack initiative, set each feature's `surface` when it differs from the initiative default. Complete the final zero-new-feature sweep and list every source file inspected. The first audit needs at least two sweeps. Keep historical feature definitions intact. In a follow-up audit, list historical anchors whose files have been removed in `retired_source_paths` and inspect their replacements.
- **Greenfield:** `baseline_kind: greenfield`, `features: []`, `unresolved: []`, `inspected_paths: ["."]`, real empty-baseline `evidence_paths`, and `requirements` with `requirement_id`, confirmed `text`, and `decision_ids` for any additional decisions. Initial discovery checks for application source to establish the empty baseline. Before planning, a revised alignment requires a fresh audit linked to the new confirmation. After planning, preserve historical requirement definitions and record the actual correction as a linked amendment. Describe the revised target in a new blueprint with explicit MODIFY/REMOVE authorization.

An existing-app audit records the confirmed requirements alongside observed A features. Give each requirement an ID distinct from every observed A feature ID. Cite actual decisions that supplement the confirmed map. For a standalone addition, use `ADD` and map it to requirement IDs only.

Use `discovery-capture --capture-file <json>` with the project root and initiative ID for UI and full-stack discovery. Start the existing app, set `P2P_APP_URL` to its origin, and use `assets/project/blueprint-discovery-capture.template.json`. Discovery setup uses browser actions `navigate`, `wait`, `fill` and `click`. Navigation stays on the app origin. Use project browser state or your app’s own login controls to establish the role. The `observations.role` and `observations.state` selectors each give an exact expected value, measured from element text or a named DOM attribute. Use a separate `ready_selector` for the visible state marker when the role or state is recorded in metadata. Different labels must be supported by distinct observed values.

Put the emitted PNG paths in the feature’s `browser_evidence`. The CLI records the browser observations and source fingerprints in the hash-locked receipt. Include any ignored or symlinked audited sources in the capture’s optional `source_paths` so the receipt can bind them. Capture every declared state and role. After an audited source change, append fresh receipts for the new source, keeping older captures in history. Capture fails if the workspace changes while the case is being set up or rendered. Text or API observations can accompany the receipts. Backend-only features continue to use API or test observations. Previously frozen audits and approvals remain readable. For a new approval against an older UI audit, append the required current capture receipts in a follow-up discovery record.

Browser captures check the build served over HTTP. The browser bypasses its local cache and service worker. It compares same-origin document, script, stylesheet and API responses to the current checkout. For static HTML, the URL can match a unique source path such as `src/items.html` for `/items`. If the app generates or transforms a response, run `browser-build-fingerprint` with the project root and initiative ID at build time. Repeat `--source-path <file>` for any extra discovery `source_paths`. Embed that value in the build and serve it as `X-P2P-Build-Fingerprint` on generated responses. The value must travel with that build and its responses, including any cached copies. Rebuild or restart when the captured source changes. Record unavailable build proof as a blocker. Earlier receipts without build evidence remain in history. New approval needs current receipts with build evidence.

Unavailable environments or unresolved behavior are blockers. Hashes protect retained files, not the truth or completeness of observations: actually inspect and test.

Show the proposed roadmap overview before saving the revision under review. Include nonempty Markdown sections named **Objective**, **User journeys**, **Scope boundary**, **Preservation constraints**, **Workstreams**, **Dependencies**, **Risks**, and **Build order**. For backend work, describe callers or service flows under **User journeys**. Explain when a section has no applicable items. For a roadmap saved under `plans/<plan-version>/`, add `[Detailed blueprint specifications](blueprints/index.md)`. `plan-record` validates the link, creates a placeholder index, and freezes the roadmap. `blueprint-record` updates the navigation index and adds each immutable blueprint version recorded against that plan. Previously frozen roadmaps stay readable. Review every workstream in the saved plan and obtain **Continue to blueprint** after the coverage and consistency check. Follow the separate blueprint, slice package and implementation authorization checkpoints.

## Detailed blueprint and coverage

Set `document_paths` to one index such as `blueprints/spec-v1/index.md` and each feature’s `spec_paths` to Markdown paths in the same version directory. Multiple features may share a document. `blueprint-record --blueprint-file` generates the index and feature documents from the structured contract, then locks the generated bytes, plan, baseline and decisions. Add supporting Mermaid source to a feature’s `diagrams` array and review it alongside the contract. Edit the structured input while drafting and use a new version or path if existing Markdown differs from the generated output. Keep earlier versions intact.

If the roadmap’s generated list of blueprint versions is missing or changed, `resume` and `validate` flag it. Run `blueprint-index-rebuild --plan-version <plan-version>` with the initiative ID and project root to rebuild the list from the frozen version records.

Each feature names stable `feature_id`, source/requirement `baseline_ids`, purpose, KEEP/MOVE/MODIFY/REMOVE or ADD classification, exact `decision_ids`, `spec_paths`, anatomy, behavior, state matrix, dependencies and acceptance checks. For KEEP or MOVE, use an empty `decision_ids` array when no feature-specific decision is needed. Plan and blueprint decision lists may also be empty when no material decisions were needed. MODIFY and REMOVE still require explicit authorization for each affected baseline behavior. The CLI embeds these contracts and the original baseline into slice packets. The generated Markdown provides the same contract for human review. Include request/precondition, transitions, validation, errors, permissions, persistence and navigation in behavior/state descriptions.

For existing A, record the observed `behavior_contract` under `behavior_contracts[feature_id]` in the discovery audit. Include the observed `backend_contract` for backend behavior. KEEP and MOVE must carry forward the same behavior and applicable backend contracts and retain every audited state. For a combined screen with distinct existing behaviors, give each behavior its own blueprint feature record and link them to the shared specification. Review those records against the Markdown, diagrams, and check expectations before approval. Use a follow-up audit to add missing contracts to an earlier audit while preserving historical evidence.

Declare `implementation_paths` for each feature using exact files or `directory/**` for a bounded subtree. Include the application and test paths the slice may change. List prerequisite blueprint features by ID in `prerequisite_feature_ids`. Leave existing service dependencies and explanatory details in `dependencies`. Resolve conflicting behavior authorizations in the journal with an explicit superseding user decision before freezing the roadmap or blueprint.

| Surface | Additional contract |
| --- | --- |
| UI | `visual_contract`: concrete `tokens`, `responsive` rules, `accessibility`, and `render_cases` with unique `case_id`, exact `route`, `state` and `viewport` width/height covering every approved state. Specifications also describe typography, dimensions, spacing, icons, labels, placement and interaction states. Proposals remain explicitly labeled until approval. |
| Backend | `backend_contract`: `request`, `response`, `authorization`, `side_effects`, `failure`, `compatibility` (including migrations/transactions where relevant). |
| Fullstack | Both contracts for a feature spanning UI and backend, with state ownership and data flow. Set a feature’s `surface` to `ui` or `backend` when only one applies. Features inherit the blueprint surface when omitted. |

New blueprints use root-level `surface_contract_version: 2`. Every feature with more than one state records `state_transitions` as an array of `{from, to, trigger, guard, effect}` objects. Each endpoint names a declared state, every declared state participates in a transition, and each trigger, guard and effect names the approved behavior. A single-state feature may omit this array or set it to `[]`.

For a sequence diagram in a slice guide, record a `sequence_contract` on the feature with the Mermaid participant IDs in `participants` and ordered `{from, to, label}` objects in `messages`. For guide format v3 diagrams using `alt`, `else`, `loop`, `opt`, `par`, `par_over`, `critical`, or `break`, also approve an ordered `controls` array. Each control event is `{type, action, position, label}`: `type` is `alt`, `loop`, `opt`, `par`, `par_over`, `critical` or `break`; `action` is `start`, `branch` or `end`; `position` is the number of preceding messages (0 means before the first message); `label` contains the start/branch condition and is empty for `end`. `else` is an `alt` branch, `and` is a `par` or `par_over` branch, and `option` is a `critical` branch. `rect` is a style-only grouping and does not change the control flow contract. The exact event order, positions and labels are checked against the diagram, so a branch or repetition cannot be added without approval. Older guide formats keep their legacy control-flow behavior unless a contract explicitly provides `controls`.

For each feature, `surface_contracts` covers its native `surface` (`ui`, `backend`, or both for `fullstack`) and each declared `slice_surfaces` entry (`api`, `mcp`, or `script`). Include every annex field listed in the implementation guide. Put the exact approved value there, or use `{"applicability":"not_applicable","reason":"..."}` with a concrete reason tied to the feature. API contracts include request, response and status/error schemas; MCP contracts include input and output schemas. The generated feature Markdown includes these contracts and transitions for review and approval. Historical blueprints without `surface_contract_version` retain their original generated Markdown and legacy validation behavior.

`acceptance_checks` contain a stable `check_id`, `kind` (`behavior`, `backend`, `visual`), exact `expected` result, and `command` argument array. Each render case also declares its `command` argument array. Use an executable or repository test adapter that observes the actual application. Visual checks can specify the approved `case_ids` they cover. An unscoped visual check applies to every case for its feature. Each case needs a visual check, and each UI feature also needs a behavior check. Backend checks use `state_expectations` to name each state they exercise and its exact expected outcome. Together, the checks for a backend-only feature must cover every declared state. A surviving backend or full-stack feature also needs a `backend_failure` expectation matching its `backend_contract.failure` text. Exercise each failure scenario and report the observed result. An approved removal instead tests the resulting absence. A backend test command emits a `states` object with the same keys and actual results. Verification checks it against the approved expectations and reruns the command.

Each acceptance check identifies the project source that measures its expected result. The CLI finds common script files named directly in command arguments. For test runners and other indirect commands, list their test files in the check's `test_source_paths`. A slice may run an existing test as read-only evidence. If delivery must create a test, list it in the feature's `planned_test_paths` and `implementation_paths` and assign it to the slice or a prerequisite. Approval and slice creation check the existing or planned source. At review, read the executed tests and confirm that they exercise every claimed outcome. For a permission check that claims two responses, exercise both roles and derive the result from their actual responses.

`blueprint-coverage --coverage-file` maps every baseline ID to feature ID and the feature's exact `acceptance_ids`. Every feature/baseline pair must be represented, including approved removals and their expected absence. No unknown, duplicate or omitted mapping is accepted. This is A-to-spec coverage, not a claim of working B parity.

Unresolved consequential questions block blueprint readiness and approval. Required feature descriptions, backend contracts, visual tokens, and responsive and accessibility rules must replace explicit draft markers such as `TBD`, `TODO: …`, and the templates’ `REPLACE …` values, including markers on their own line inside longer descriptions. Source facts and explicit user intent constrain proposed tokens and architecture; never make the fresh implementer invent material details. Seek permission before any preapproval disposable runnable spike, and preserve it as isolated experiment evidence only.

## Approval, implementation and verification

Finish the [workstream walkthrough and cross-workstream consistency check](guided-design-review.md#blueprint-walkthrough) before requesting formal approval. After recording coverage, run `validate` and link the generated blueprint index, feature specifications and exact coverage record. Save the decision recap in a separate Markdown file and show it with the exact version and remaining limitations. Wait for explicit user approval. Use the blueprint approval template to record the actual user decision. Put every displayed blueprint index and feature spec, the frozen coverage record, the consistency report and the recap file in `shown_paths`. Set `workstream_consistency_path` to the report and `decision_recap_path` to the recap. Record expressly approved exceptions in `exceptions`, using an empty list when there are none. Approval freezes the displayed files and the plan, decisions, baseline and coverage hashes.

After approval in a new blueprint initiative, follow [conversational slice review](slice-review-workflow.md). Complete the entire proposed inventory, review the exact guides, reconcile the collection, record the user's package approval, lock it, and wait for separate start authorization. Release each assignment from the authorized package. For a legacy blueprint initiative using its original delivery policy, `slice-create` continues to use `assets/project/blueprint-slice.template.json`. Offer [explicit migration](slice-review-workflow.md#legacy-migration) without editing legacy receipts.

An independent reviewer runs the approved checks, inspects the results, and supplies `test_source_paths` and a slice-local `output_file` per check. Each approved command prints one JSON object with `check_id`, `expected`, measured `actual`, and `result` to standard output. Send diagnostic logs to standard error. `reconcile --action verify` runs the exact approved argument arrays from the application root without a shell. A failed command or a result that differs from the reviewed observation blocks verification. Include deleted and renamed source paths in the worker report's `implementation_paths`. The paths must have existed at approval and be within the slice's ownership. Verification records their absence, and recreating a recorded deletion invalidates the receipt. `accept`, `resume`, and `validate` check the saved receipt and source state without running commands again.

Approval freezes a workspace file inventory. In Git, this covers tracked files and unignored untracked files under the project root. Verification blocks changes outside the assigned slice paths and requires the worker report to list every changed file within its own paths, including changed test files. Agree on the treatment of unrelated workspace changes before approval and use the same workspace baseline for delivery. Earlier blueprint approvals issued without a workspace snapshot require a new version and approval for new delivery.

Before writing shared UI source, use [Cross-Screen Visual Regression Protection](cross-screen-regression.md). Review the actual consumers and capture the original application before the edit. Cite the change ID in the slice handoff.

For each implemented UI slice, complete the [Visual Integrity Gate](visual-integrity.md) alongside the rendered cases. Put explicitly approved browser outcomes in the applicable render case's `interaction_assertions` array and include the steps that produce those outcomes. The register preserves clean inspections, repair attempts and unresolved findings across sessions.

For UI, provide reviewed `rendered_cases` with distinct PNG and DOM/style JSON files. Set `P2P_APP_URL` to the running application’s origin. UI verification requires Node.js 22 or later and Chrome or Chromium on PATH, with `P2P_CHROMIUM` available to select the executable. The CLI opens the approved route in a fresh browser at the approved viewport and runs the case’s setup command. The command can use `P2P_BROWSER_ENDPOINT` or the `P2P_BROWSER_PAGE` DevTools WebSocket URL to establish the approved interaction state. Leave the page open and the application running. The CLI requires the case’s `ready_selector` to match a CSS-visible element with positive area inside the approved viewport after ancestor clipping, measures each approved visual check’s computed CSS `property` at its `selector`, and captures its own PNG. If Chrome cannot confirm that the marker is unobstructed, the CLI checks that the marker contributes pixels to the screenshot. It compares captures with the marker present, temporarily transparent, and restored. The same visibility and screenshot checks apply to each visual measurement target by default. To verify an intentionally hidden element, set `measurement.visibility` to `hidden` and name the exact CSS outcome. The CLI saves the approved measurements and the original PNG with the receipt. The served build is checked using the same response evidence as discovery, with the workspace as it exists during verification. Record `specification_limits` and review responsive and accessibility interactions beyond the computed styles. Backend-only slices use test/API output and source hashes.

When KEEP or MOVE preserves an audited UI feature for more than one role, include render cases for every observed role and state pair. In each case, name the `role`, copy or map the discovery `observations` for the role and state to live selectors, and retain the discovery `ready_selector` as a stable marker for the preserved control. Use an approved browser setup command or the `setup` actions to establish the role. Put the case role in both the review and its DOM evidence. Use fresh approval for earlier multi-role specs that do not carry these checks.

A newly discovered gap uses `missing-feature`, preserves old approval records, blocks implementation and triggers a full affected-scope re-audit with one full zero-new sweep. A real gap needs a new blueprint/coverage version and fresh approval; a false report requires a fresh actual user correction explicitly naming the open `report_id`, `resolution: not_missing`, affected behavior IDs and evidence. A generic earlier design decision cannot dismiss a report. Record that report-bound correction through `conversation-record`, then name its decision ID in `missing_report_resolutions`. A report correction can retain the active approval when its follow-up audit preserves the approved behavior, scope and source fingerprints. Other follow-up audits require a fresh approval even when the feature IDs are unchanged. Fresh approval retires earlier slice assignments and releases their paths. In reviewed mode, create and lock a newly validated package and obtain new start authorization before continuing. Old contracts, approvals and receipts remain in history. Bind new slices to the active approval and verify its full coverage before integration.

## Continuity

Use `work-update` before and after meaningful work and before long operations. Blueprint transitions update the active task’s phase and next action with the manifest and retain its recorded steps, files and unresolved question. A `waiting_user` cursor links the open exchange through `pending_question_id`. Both resume formats show outstanding questions and the exact recorded answer for the active waiting task when it exists. Use that answer to update the same work cursor. JSON resume also returns original exchanges, `conversation_usage` linking them to plans, blueprints and slices, and `coverage_with_slices` linking each approved baseline/feature/check row to its slices. These views derive from locked records and preserve the original exchange and coverage bytes. Resume and validation compare saved cursor hashes and the source linked to questions until their waiting task resumes. To checkpoint an intended deletion or rename, list the previously tracked path in `absent_code_paths` and keep the new path in `code_paths`. Retain the expected absence in later updates until the path is explicitly restored.

Evidence lives in the ignored initiative directory in the target app, not the installed skill or tracked documentation paths. Transfer the whole directory with verified hashes for independent worktrees or machines; ignored artifacts are not cloned by Git. See [continuity.md](continuity.md) for canonical blockers, checkpoints and portability.


Run the [Final Visual Quality Audit](visual-quality.md) after entering integration. Before entering integration, accepted slice contracts must cover every feature/acceptance-check pair in the active approval; creating and accepting only some slices is not completion. Explicit defect/dependency blockers require resolution and reporting before verification. A waiting/blocked work cursor prevents roadmap, blueprint, approval and delivery transitions while conversation and blocker-resolution records remain available.

Resume, validation, approval, and slice creation recheck live fingerprints for audited source outside the assigned slice paths. Source within those paths can change during approved implementation and is checked against the slice and its verification receipt. If all assignments are cancelled or approval is withdrawn, reconcile changed source with a new audit before reapproval. Withdrawn slice paths cannot exempt source from the freshness check. For new delivery from an earlier handwritten blueprint or an earlier UI contract, generate a new version with the current document and browser contracts and obtain fresh approval.

Approval, withdrawal, missing-feature reporting, and explicit defect blocking stage their file and journal changes before committing. If one is interrupted, workflow commands pause until the original command is retried with the same input. Recovery verifies the saved files and journal boundary, then completes the transition once. For initiatives interrupted by earlier CLI versions, inconsistent history blocks delivery and can require restoring a consistent backup and replaying the recorded action. If another write is interrupted, validation detects orphan records and journal/manifest disagreement. Preserve the original record and retry its original command with the exact same input and intact referenced evidence; recovery reuses its original bytes/hash and appends only missing history. An interrupted legacy blueprint slice assignment supports retrying `slice-create` with the original contract input. Recovery checks the saved contract and completes the same cursor transition. A changed retry is blocked for explicit reconciliation. Never delete the recorded answer to make a retry succeed. The local journal and source archives are durable evidence, not an automatic backup or transcript hook.


## Protected visual decisions

During blueprint discussion, identify explicitly approved exceptions to existing visual or interaction patterns. Confirm uncertain intent with the user. Record each exception on the decided A+ exchange with affected feature or requirement IDs and a `protected_visual_decisions` array. Each entry contains `decision_id`, a stable scoped `component` name, the exact `property`, its approved `requirement`, the `purpose` and an observable `verification`. Use separate entries for properties that can change independently.

For example, a user can approve a rounded ERP menu trigger and require a single dropdown with a specific option order. Record those as separate protected properties. A spacing repair can preserve all three. The generated blueprint includes the applicable decisions and the source A+ exchange IDs. Surface them in the blueprint recap and include them in every affected slice guide. Resolve incompatible approved requirements by recording the user's explicit correction linked with `supersedes`. Carry forward or revise each protected decision by ID, then revalidate and obtain the affected approvals through the amendment workflow.
